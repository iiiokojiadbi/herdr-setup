# MCP для Codex-воркера

Адаптер в `mcp/worker/` использует официальный TypeScript SDK 1.32.2 и общий
`createClient` из `core/`. SDK обслуживает initialize, capabilities, tools/list,
tools/call и JSON-RPC по stdio. stdout содержит только протокол; диагностика
идет в stderr без входных аргументов и окружения.

Нужны Linux, Node.js 22+, npm, `flock` из util-linux и `hc` в PATH.
Соберите checkout и оставьте его на постоянном месте:

```bash
npm ci
npm run build
npm test
# Общая проверка также требует декларацию установленного движка модов:
MOD_API_TYPES=/absolute/path/to/runtime-api.d.ts npm run typecheck
```

`dist/herdr-worker-mcp/launcher.mjs` — исполняемый launcher. Ядро встроено в
`server.mjs`; SDK остается runtime-зависимостью в node_modules этого checkout.
Оба файла dist и node_modules нужны после установки. Прямой запуск server.mjs
обходит обязательную блокировку журнала и не поддерживается.

## Установка профиля

Генератор по умолчанию ничего не пишет. Для существующего профиля:

```bash
node scripts/install-worker-mcp.mjs --dry-run ~/.codex/worker.config.toml
node scripts/install-worker-mcp.mjs --write ~/.codex/worker.config.toml
node scripts/install-worker-mcp.mjs --check ~/.codex/worker.config.toml
```

Без пути `--dry-run` печатает отдельный фрагмент. `--check`: код 0 означает
совпадение нужных настроек, 1 — требуется установка, 2 — ошибка. `--write`
идемпотентен, атомарно обновляет существующий файл, проверяет изменение файла
перед заменой и сохраняет права. Настройки размещаются в блоке
`# BEGIN managed herdr-worker MCP` / `# END managed herdr-worker MCP` в конце
файла. Маркеры распознаются только как отдельные строки вне строковых
значений TOML; примеры в multiline string и упоминания в комментариях
игнорируются. Пробельный суффикс после END сохраняется побайтно, включая
CRLF и пустые строки. Вне блока исходный TOML сохраняется побайтно, включая комментарии,
переводы строк, `1.0` и int64. При необходимости перед блоком добавляется
перевод строки. Парсер используется только для проверки и поиска конфликтов,
с поддержкой больших целых через BigInt; весь профиль не пересериализуется.

Блок принадлежит установщику: command, enabled, enabled_tools, env_vars и
approval_mode двух инструментов. Посторонние настройки внутри блока или
таблицы после него вызывают отказ без изменения файла. Полностью совместимая
существующая unmanaged-таблица herdr-worker остается неизменной. Несовместимую
unmanaged-таблицу установщик автоматически не переписывает: сгенерируйте
фрагмент `--dry-run` без пути и вручную перенесите необходимые ключи, сохранив
остальные настройки. После этого `--check` примет совместимую таблицу.
Конфликтующие URL, непустые args, наличие HC_PARENT или HC_TERMINAL_ID в env
(включая пустую строку) и запрет инструментов требуют ручного разрешения.

Фрагмент содержит `[mcp_servers.herdr-worker]`, абсолютный command на launcher,
`env_vars = ["HC_TERMINAL_ID", "HC_PARENT"]`,
`enabled_tools = ["report", "ask_owner"]`. Для каждого инструмента
`tools.<name>.approval_mode = "approve"` разрешает вызов без дополнительного
подтверждения; общая approval_policy профиля не меняется. Схема настроек
проверена командой `codex mcp get` на CLI 0.169.0.

Профиль должен подключаться штатной оберткой роли: сам Codex не выбирает
произвольный `<role>.config.toml` автоматически. После установки нужна новая
сессия воркера с переданными HC_TERMINAL_ID и HC_PARENT.

## Доставка и журнал

`report(text, blocker?, requestId?)` и `ask_owner(text, requestId?)` вызывают
только `hc send --json -- $HC_PARENT <сообщение>`. Получателя задать нельзя.
`ask_owner` завершается после отправки: ответ приходит отдельным вводом hc.
Без адреса терминала возвращается NOT_IN_HERDR, без родителя — NO_PARENT.

Схемы плоские, без oneOf/anyOf/not. Лимиты core: текст 32768 символов,
requestId 128, непустые строки без NUL. Поле JSON Schema `type` и MCP
content `type` — обязательные поля внешних стандартов, идентификаторы кода
так не называются. Ответы — общий JSON-конверт в text content; ошибки
доставки отмечены isError. Неизвестный инструмент — JSON-RPC InvalidParams,
неизвестный метод — MethodNotFound, обработку протокола выполняет SDK.

Журнал: `$XDG_STATE_HOME/herdr-core/worker-mcp`, иначе
`~/.local/state/herdr-core/worker-mcp`. Собственный подкаталог отделяет журнал
от launch passports и других файлов ядра. Профилям с writable_roots на
`~/.local/state/herdr-core` дополнительный грант не нужен. Явный XDG_STATE_HOME
остается поддерживаемым; внешний каталог состояния должен быть доступен
для записи. Установщик sandbox не меняет. При отказе записи сервер завершает
запуск. Права родительского каталога и его файлы launcher не меняет.
Каталог 0700, файлы 0600. Имя файла — SHA-256 пары терминал/родитель.
Launcher берет эксклюзивный неблокирующий flock на все время жизни сервера.
Второй процесс для той же пары завершается с ошибкой; другие воркеры могут
работать параллельно. Lock-файл не удаляется: блокировка снимается ядром при
выходе процесса. Все доставки внутри сервера сериализует общий клиент.

До hc send на диск синхронно сохраняется pending: временный файл в том же
каталоге, fsync, rename, fsync каталога. После отправки сохраняется sent либо
unknown. На старте abandoned pending становится unknown, повторной отправки
нет. Поврежденный или слишком большой журнал блокирует запуск; молча
очищать его нельзя. Записи содержат только отпечаток ключа, payloadHash,
время, статус и признак неявного ключа. Текст, исходный requestId, окружение,
секреты из hc stderr и полный конверт на диск не попадают. requestId должен
быть непрозрачным идентификатором, а не секретом; fingerprint не шифрование.

TTL, вытеснение и пределы переиспользуют core: семь дней, 500 записей,
1 МиБ. Read-limit 2 МиБ защищает загрузку поврежденного файла. При очистке
молодые pending защищены десять минут. Для MCP лимит числа записей жесткий:
один процесс владеет журналом и последовательно выполняет операции.
Для сравнения записей при обновлении core использует канонический ключ
адаптера: исходный ключ и его отпечаток из entries учитываются как одна запись.
Дедупликация после TTL или вытеснения не гарантируется. Без requestId окно
60 секунд, включая unknown; явный ключ сохраняет unknown до TTL/вытеснения.
Другой payload с тем же ключом — REQUEST_ID_CONFLICT. Сбой hc, timeout или
сбой сохранения после отправки — DELIVERY_UNKNOWN: слепо повторять нельзя.

Стабильный session id Codex не передается этим профилем и не предполагается.
Область журнала — время использования пары HC_TERMINAL_ID/HC_PARENT, а не
разговор Codex. Рестарт процесса сохраняет дедупликацию; новый разговор в
том же терминале тоже видит старые ключи. Используйте уникальные requestId
между разговорами. Новый терминал или родитель меняет область: защита от
повторной доставки между ними отсутствует. Exactly-once не обещается.
При смене каталога состояния старый журнал также перестает участвовать.

## Проверка и живая приемка

`npm test` собирает dist и проверяет SDK handshake/list/call, fake transport,
отказы входа/окружения, dedup/conflict/unknown, рестарт, восстановление
pending, права файлов, чистоту stdout, настоящий неуспешный subprocess hc,
блокировку второго сервера и выход по EOF. Терминалы тесты не создают.

Перед живой установкой ведущий проверяет dry-run, затем устанавливает
фрагмент в роль. В разрешенной сессии CLI 0.169.0 надо проверить наличие
двух инструментов, отправить report с явным requestId, повторить его и
подтвердить один отчет у родителя. Затем ask_owner: вызов должен завершиться
после отправки, ответ родителя должен прийти отдельным вводом. Проверить
blocker и рестарт MCP с повтором ключа. Сборка и чтение конфигурации не
заменяют эту приемку.

Живая приемка на `codex-analyst` подтвердила доставку `report`, повтор с
`duplicate:true` без второго отчета и `ask_owner` с ответом отдельным вводом.
Фактические имена в TUI: `mcp__herdr_worker__report` и
`mcp__herdr_worker__ask_owner`. Тот же managed block установлен и проверен
`--check` у `codex-coder` и `codex-reviewer`. Сессии, запущенные до изменения
профиля, продолжают работать со старой конфигурацией; новые получают MCP при
старте.
