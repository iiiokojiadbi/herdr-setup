# Herdr worker tools

Два мода для управления воркерами через `hc`. Общее ядро собирает аргументы без shell, проверяет принадлежность терминалов и возвращает стабильный конверт результата.

Нужны Node.js 22+, npm, `hc` в PATH и движок модов версии 2.1.322. При обновлении движка повторите проверку типов и валидацию.

```bash
npm install
npm run build
MOD_API_TYPES=/absolute/path/to/runtime-api.d.ts npm run typecheck
npm test
claude plugin validate dist/herdr-orchestrator
claude plugin validate dist/herdr-worker
```

`MOD_API_TYPES` указывает на декларации установленного движка из встроенного навыка `plugin-authoring` (`types/claude-code.d.ts`). Первый запуск копирует их в кеш `node_modules`; последующие `npm run typecheck` используют кеш. Декларации в репозиторий не входят. Сборка встраивает ядро в каждый плагин, внешних runtime-импортов нет.

Установка из общего marketplace:

```bash
claude plugin marketplace add iiiokojiadbi/claude-plugins
claude plugin install herdr-orchestrator@iiiokojiadbi --scope user
claude plugin install herdr-worker@iiiokojiadbi --scope user
```

Собранные `dist` закоммичены в репозиторий, marketplace берет их по тегу `herdr--v0.1.0`.

Локальная сборка для разработки: `node scripts/install.mjs` печатает команды для текущего checkout и ничего не устанавливает:

```bash
claude plugin marketplace add /absolute/path/to/checkout
claude plugin install herdr-orchestrator@herdr-setup --scope user
claude plugin install herdr-worker@herdr-setup --scope user
claude plugin enable herdr-orchestrator@herdr-setup --scope user
claude plugin enable herdr-worker@herdr-setup --scope user
```

В пользовательские настройки добавьте allow-правила, сохранив остальные настройки:

```json
{"permissions":{"allow":["mcp__herdr-orchestrator__*","mcp__herdr-worker__*"]}}
```

Затем `/reload-plugins`. Локальный marketplace использует относительные пути к `dist`; сохраняйте checkout с собранными артефактами. Для разработки передайте обе папки через повторенный `--plugin-dir`.

Без `HC_TERMINAL_ID` инструменты не регистрируются. При пустом `HC_PARENT` доступны семь инструментов ведущего: `worker_spawn`, `worker_list`, `worker_send`, `worker_wait`, `worker_read`, `worker_stop`, `worker_templates`. При заданном `HC_PARENT` доступны только `report` и `ask_owner`. Вложенные агенты получают отказ. Перед изменяющей операцией проверяются разрешения движка.

Основной режим — push и snapshot. Отчеты и аварийные события воркера `hc` доставляет ведущему отдельным вводом; после `worker_spawn` или `worker_send` ведущий продолжает независимую работу либо завершает текущий ход. `worker_wait` зарегистрирован как deferred: это блокирующая диагностическая тулза, не основной способ получить результат. Для сверки служит неблокирующий `worker_list`. `done` и `idle` не доказывают успех задачи.

`worker_spawn` принимает шаблон и первую задачу либо массив аргументов программы без задачи. Один элемент `command` должен соответствовать `^[A-Za-z0-9._/-]+$`: только латинские буквы, цифры, точка, подчеркивание, дефис и косая черта. Значения `runner*`, `runner?`, `~`, `#comment` отклоняются: `hc` трактует одиночный аргумент как shell-строку. При двух и более элементах каждый передается отдельным argv. `worktree` — корень существующего Git checkout; мод его не создает. `worker_list` без аргументов возвращает живых детей текущего терминала; `address` дает снимок одного своего ребенка, `includeFinished: true` добавляет `finished`/`exited`/`dead` в снимок или в общий список. Без `includeFinished` завершенный ребенок по `address` дает `FINISHED`; `not_found` остается ошибкой `NOT_FOUND`, а не успешным завершением. Снимок несет нормализованные `state`, `status`, `turn`, `firstMessage`, `exitCode`, `finishedMs`, `reason` и `signal` — только те поля, которые отдает `hc`. `worker_stop` вызывайте только по явной просьбе пользователя; удаление записи требует `remove: true`.

Инструменты возвращают JSON-строку с конвертом `{ok:true,data}` или `{ok:false,error,data}`. При `ok:false` ответ инструмента помечается `isError: true`. Ошибка с `effect: applied` несет частичный результат; `unknown` запрещает слепой повтор. `worker_wait` — блокирующая диагностика, а не основной режим: по умолчанию ждет любого ребенка 180 секунд, максимум 540 секунд; контрольный таймаут — обычный результат. Ответ подсказывает продолжить работу и сверить состояние через `worker_list`, а не ждать по кругу.

Отчеты идут только родителю. Повтор с тем же `requestId` и содержимым не отправляется заново; другое содержимое с тем же ключом дает конфликт. Без `requestId` используется хэш содержимого и окно 60 секунд, включая `unknown` и `pending`; после окна тот же текст отправляется заново. Явный `requestId` сохраняет `unknown` и `pending` без повторной отправки до TTL. Журнал отделяет сессии через `session.id`, сохраняет ключи при reload и хранит хэш вместо полного текста. Срок хранения — до семи дней, целевой лимит 500 записей и бюджет 1 МиБ UTF-8 JSON. При старте и очистке удаляются записи старого формата без сессии. Перед записью удаляются старейшие записи, не помещающиеся в бюджет, кроме `pending` моложе 10 минут. Чужие активные `pending` сохраняются и при старте другой сессии. Если места для новой записи нет, `JOURNAL_FULL` с `effect: none` возвращается до отправки; дождитесь завершения активных доставок и повторите с тем же `requestId`. После вытеснения дедупликация старого ключа больше не гарантируется. В пределах срока хранения неизвестный исход доставки остается неизвестным после перезагрузки: гарантии exactly-once у `hc` нет. Новый `requestId` может повторить доставку. Лимиты: текст 32768 символов, экран 65536 символов, история 1000 строк.

Общий store не предоставляет атомарный compare-and-swap: защита журнала — best-effort. Перед удалением запись перечитывается; если `timestamp`, `status` или `payloadHash` изменились, очистка пропускает запись. Между перечитыванием и удалением остается окно гонки. Лимит 500 записей мягкий: при 499 защищенных `pending` два параллельных резервирования последнего места могут оба пройти и оставить 501 запись. Бюджет 1 МиБ оставляет запас до ограничения store 4 МиБ; в этом сценарии переполнения по байтам нет. Строгая гарантия потребовала бы внешней блокировки, которой в MVP нет.

Тесты используют fake transport и не создают терминалов. Живую проверку ролей, разрешений, первой задачи и доставки отчета выполняйте отдельно в разрешенной среде.
